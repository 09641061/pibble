# Decision: Schema migrations with Flyway

Status: implemented

## Problem

A schema generated by Hibernate cannot change a database that holds data, has no reviewed history, and cannot express several invariants Takodu relies on (exclusion constraints, partial unique indexes, `CHECK`s).

## Decision

Flyway owns the schema. `quarkus-flyway` runs plain SQL scripts from `src/main/resources/db/migration` at startup in every profile (`quarkus.flyway.migrate-at-start=true`), and Hibernate only validates the entities against the result (`quarkus.hibernate-orm.schema-management.strategy=validate`), so a mismatch fails at startup. Each context gets one file when it is created, copied from the product docs' `schema.sql`, then one file per later change. The version is the UTC creation time (`V202610211430__iam.sql`), so two branches never take the same number; a branch whose migration is older than one merged meanwhile renames it before merging.

Schema conventions: `uuid` primary keys; `timestamptz` for instants and `time` for local opening hours; money as integer cents plus an ISO currency; enumerations as `text` with a `CHECK`; `created_at` and `updated_at` on every table (the columns of `AuditableAbstractPersistenceEntity`); soft delete only where history must survive (`customers.deleted_at`, `members.removed_at`, `establishments.archived_at`). The [takodu-migrations](../../../.agents/skills/takodu-migrations/SKILL.md) skill has the detail.

## Alternatives considered

**Hibernate `update` in prod.** It does not drop columns, does not migrate data, cannot create exclusion constraints and applies changes without review.

**Sequential versions (`V1`, `V2`, …).** Simple to read, but two parallel branches both add `V7` and the second merge breaks startup.

**Liquibase.** It works as well, but XML or YAML changelogs are more verbose than plain SQL for a team that already writes SQL.

## Consequences

Dev, test and prod build the schema the same way, and `SchemaMigrationsTest` fails when a migration is pending or its checksum changed. Every entity change needs a migration in the same commit, and a committed migration can never be edited. Tests of the constraints themselves arrive with the contexts that own them, such as booking's exclusion constraint.
